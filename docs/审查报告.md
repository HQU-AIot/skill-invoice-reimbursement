# 审查报告

审查对象：内部版本的 `invoice-reimbursement` skill（安装于 `~/.agents/skills/invoice-reimbursement`）。

审查目的：在公开发布到 GitHub 前，确认流程是否自洽、脚本是否可靠、文档是否可执行、示例是否泄露真实信息。

结论：**流程设计成熟，可以作为公开 skill 发布；但内部版本存在 4 个 P1 问题（2 个已实测复现）、若干 P2 一致性问题，以及真实单位/税号/票号泄露风险。** 本仓库是脱敏、修复后的发布版；内部版本未被修改。

## 2. 总体评价

### 2.1 做得好的地方

1. **三层核对模型清晰**：发票合规 → 三方一致 → 交付证据链。这不是“改名脚本”，而是可审计的流程。
2. **非破坏性**：重复、待补、取消、不报销全部隔离，不删除；交付夹可重建。
3. **版式兼容有实战价值**：常规版式 + 标签/数值分离版式，用中文大写反查小写，解决了真实 PDF 文本层顺序错乱的问题。
4. **manifest 单一数据源**：工作簿、交付夹、终审都围绕它，避免多处手改。
5. **交付协议具体**：扁平命名、三件套、MD5 同步、逐张 PDF 复解析，都是财务场景真正需要的检查。
6. **坑文档很实用**：全角/半角、Excel 锁、OFD 转换、同金额不同交易、发票预览等，都是踩过的坑。
7. **财务报表极简**：只保留已报销项目，不把工作底稿塞给财务，这是正确的产品判断。
8. **脚本小、可读、无网络**：没有隐藏依赖和遥测，容易审计和修改。

### 2.2 主要风险

- 内部版本把真实单位、税号、发票号、订单号、商家名、项目统计写进了文档和示例；直接公开会泄露项目信息。
- 交付构建在缺支付路径时会崩溃，而不是给出可读的问题。
- 终审对图片发票和同号不同文件的处理不完整，可能产生假失败或漏检。
- 文档与脚本在字段要求、号码位数、日期口径上存在不一致。

## 3. 问题清单

> 行号以内部版本为准；发布版已修复的项在“状态”中注明。P1 = 发布前应修；P2 = 应修/应对齐；P3 = 建议改进。

### P1

#### P1-1 空支付路径导致构建脚本崩溃

- **位置**：`scripts/build_delivery.py:90-96`
- **现象**：`payment_file` 为空字符串时，`root / ""` 得到项目根目录；`pay.exists()` 为真，`shutil.copy2(pay, dst)` 尝试复制目录，抛 `PermissionError`/`IsADirectoryError`。
- **影响**：manifest 少填一个字段，整个构建中断，且错误信息不指向真正原因。
- **实测**：已复现（`PermissionError: [Errno 13] Permission denied: ...\root`）。
- **修复**：发布版先判断 `pay_rel` 非空且 `is_file()`；发票、订单、附件、工作簿同样处理。现在输出 `missing payment: (empty)`，退出码 1，不崩溃。

#### P1-2 备份命令把目录复制进自己

- **位置**：`references/workflow.md:10-12`（`SKILL.md:89-92` 也有类似写法）
- **现象**：`cd 发票汇总 && cp -r . _原始备份_$(date +%Y%m%d)` 的目标在源目录内部。
- **影响**：报错并留下空备份目录；如果用户忽略错误继续操作，以为已有备份，风险很高。
- **实测**：已复现（`cp: cannot copy a directory, '.', into itself, '_backup'`）。
- **修复**：文档改为先复制到同级目录，再 `mv` 进项目；并明确写出错误写法。

#### P1-3 终审只累加 PDF，图片发票造成假失败

- **位置**：`scripts/check_delivery.py:85-96`、`:120-121`
- **现象**：只有 `.pdf` 且解析成功时才累加 `total`；PNG/JPG 发票金额被当作 0，最终 `PDF total != manifest total`。
- **影响**：混合格式项目终审必然 FAIL，用户可能误以为金额错了。
- **修复**：发布版只比较“成功解析的 PDF 金额”与“这些 PDF 的 manifest 金额”；非 PDF 给 WARN；新增 `--require-pdf` 可把非 PDF 判为 ERROR。

#### P1-4 真实单位/税号/票号/项目统计泄露

- **位置**：
  - `SKILL.md:112`、`:290`、`:297-304`、`:313-315`
  - `references/manifest-schema.md:9-10`、`:37-45`、`:76-78`、`:99`
  - `references/workflow.md:119`、`:129-137`、`:161`、`:279`、`:331-332`、`:356`
  - `references/verification.md:10`、`:99`、`:109`
  - `references/pitfalls.md:75`、`:80`、`:90`
  - `references/naming-and-folders.md:14-16`
  - `scripts/parse_invoice.py:8`、`:188`；`scripts/check_delivery.py:16`
- **现象**：真实单位名称、统一社会信用代码、发票号码、订单号、销售方、商品名、项目张数（39/8/2）直接写在 skill 里。
- **影响**：公开仓库会暴露项目与单位信息；也降低 skill 的通用性。
- **修复**：发布版统一替换为 `示例单位`、`91110000XXXXXXXXXX`、`12345678901234567890`、`示例电子科技有限公司` 等虚构值；项目统计改为 `N`；示例日期/商品名通用化。

### P2

#### P2-1 工作簿合计取“最后一个数字”

- **位置**：`scripts/check_delivery.py:136-143`
- **现象**：在“合计”行里遍历所有数值，最后一个 > 0 的赋给 `total_cell`。如果金额列后面还有数量等数字，会取错。
- **实测**：合计行 `["合计","2 张",30.5,2]`，旧实现得到 `2.0` 而不是 `30.5`。
- **修复**：发布版先找表头“价格/金额”列，再读该列；找不到才回退到最后一个数字，并给出 WARN。

#### P2-2 工作簿行数只认整数

- **位置**：`scripts/check_delivery.py:142`
- **现象**：`isinstance(values[0], int)`；序号存成 `"01"` 或 `1.0` 时统计为 0。
- **影响**：财务/Excel 模板常用文本序号，终审会误报“行数不符”。
- **修复**：发布版 `to_int()` 兼容 `1`、`1.0`、`"01"`。

#### P2-3 详情数量未比对，且排序是字典序

- **位置**：`scripts/check_delivery.py:107-115`
- **现象**：`zip(order_srcs, details)` 会静默忽略多余/缺失；`sorted(glob("*-详情*"))` 把 `详情10` 排在 `详情2` 前面。
- **影响**：交付夹多一张旧详情也能 PASS；10 张以上详情时 MD5 对错行。
- **修复**：发布版数量不等直接 ERROR；按 `详情N` 的数字排序。

#### P2-4 购方名称未真正校验；税号回退可能取错

- **位置**：`scripts/parse_invoice.py:143-164`
- **现象**：`expected_buyer_name` 只在 `buyer` 为空时用作回退，不参与 `checks`；税号回退取第一个 15–20 位 token，可能是发票号或销售方税号；号码固定要求 20 位。
- **影响**：抬头错但票面有其他名称时可能不报；老票被判不合规；报告字段可能误导。
- **修复**：发布版传 `--buyer-name` 时增加 `buyer_name` 检查；税号候选排除发票号；号码支持 8/10/12/20 位；买方/卖方名称提取更稳健。

#### P2-5 `dedupe.py --apply` 不处理同号不同文件

- **位置**：`scripts/dedupe.py:129-142`
- **现象**：只遍历 `dup_files`（MD5 组），`dup_invoices` 只报告不移动。
- **影响**：文档说“两种重复都要查”，用户可能以为 `--apply` 都处理了。
- **修复**：发布版保留保守行为，但移动后明确提示“同号不同文件未移动，请人工处理”；文档同步说明。

#### P2-6 manifest 字段要求与示例不一致

- **位置**：`references/manifest-schema.md:56-58` vs `SKILL.md:292-307`
- **现象**：schema 把 `purpose`、`qty` 标为必填，SKILL 示例没有；`build_delivery.py:98-106` 使用 `extra_files`，schema 未记录。
- **影响**：按示例写 manifest 会缺字段；额外附件无法被使用者发现。
- **修复**：发布版补齐示例字段，并在 schema 中记录 `extra_files`、`status`、`payment_file` 约束。

#### P2-7 外部 `xlsx.py validate` 依赖

- **位置**：`SKILL.md:211`、`references/workflow.md:358`
- **现象**：要求用 `xlsx.py validate` 校验工作簿，但该脚本不属于本 skill。
- **影响**：独立使用者无法执行；文档看起来像缺文件。
- **修复**：发布版改为“回读校验：单表、行数、序号、合计、格式”，并说明由 Agent 或 openpyxl 完成。

#### P2-8 日期校验口径不一致

- **位置**：`SKILL.md:114` vs `references/verification.md:11`
- **现象**：SKILL 写“开票日期不早于订单付款日期”，verification 写“后补开票允许，先开票后付款需警惕”。
- **影响**：执行者不知道哪条是硬规则。
- **修复**：发布版统一为“关系合理；后补开票常见；先开票后付款需在报告说明”，不再作为自动硬失败。

#### P2-9 项目统计数字写进通用文档

- **位置**：`SKILL.md:203`、`references/workflow.md:279`、`:356`
- **现象**：文档里写死了具体项目的张数、待补数量和数据行数，而不是用 `N` 表示。
- **影响**：公开后误导使用者；项目变化后文档过期。
- **修复**：发布版改为 `N`/“待补项”。

#### P2-10 缺工作簿/报告生成脚本

- **位置**：`SKILL.md` 第 7、8 步；`scripts/build_delivery.py`
- **现象**：工作簿和四份文本报告由 Agent 按规范生成，没有可重复的一键脚本；`build_delivery.py` 也不生成 `00-报销说明.txt`。
- **影响**：不同批次/不同 Agent 的输出可能不一致；无法用 CI 验证。
- **状态**：未在 v1.0.0 实现，列入路线图（`build_workbook.py`、`build_reports.py`）。文档已明确说明边界。

#### P2-11 缺 requirements/tests/license

- **位置**：仓库根目录
- **现象**：没有依赖清单、测试、许可证。
- **影响**：新用户不知道装什么；改动无回归保障；公开仓库缺少授权声明。
- **修复**：发布版新增 `requirements.txt`、`tests/test_scripts.py` 和 MIT `LICENSE`（版权人可按需调整）。

## 7. 结论

这套 skill 的核心价值不在“识别”，而在 **把报销变成可验证的证据链**。内部版本的流程、目录契约、报表口径和交付协议已经成熟；主要问题是工程边界（空路径、图片发票、同号去重）、文档一致性，以及公开发布前的脱敏。

发布版已经修复 P1、P2 中可在代码层解决的问题，并补齐了技术文档、使用文档、演示脚本、测试和示例。剩余问题（工作簿/报告一键生成、同号去重策略、OCR 回退）已明确列入路线图，不影响 v1.0.0 作为“Agent Skill + 可审计脚本”发布。
